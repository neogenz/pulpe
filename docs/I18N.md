# Internationalisation — FR / EN / DE / IT

French is the source language and the fallback for every missing key, on every platform. This
document owns the decisions the three surfaces share and the translation of the product
lexicon. Platform mechanics live beside the platform code.

## Cross-cutting contract

| Decision             | Value                                                                                                                |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Language codes       | ISO 639-1, bare: `fr` `en` `de` `it`. Never a regional variant.                                                      |
| Default and fallback | `fr`, after stored preference, incoming CTA and device/browser detection have all failed.                            |
| Preference key       | `locale`, on `PUT /v1/users/settings`, stored in owner-scoped `public.user_locale_preference`.                       |
| Boot render source   | The local snapshot (`localStorage` / `UserDefaults`); the server is the source of truth.                             |
| Write timing         | Immediately on change, not on screen exit.                                                                           |
| Single definition    | `SUPPORTED_LOCALES` and `supportedLocaleSchema` in `shared/schemas.ts`, `LOCALE_METADATA` in `shared/src/locale.ts`. |

No regional variant, because the region already comes from the currency: `CHF` formats through
`de-CH` on the web and `fr_CH` on iOS (both render `1'234.50`), `EUR` through `fr-FR`. A
`de-CH` here would open a second regional axis that could contradict the first.

### Amounts follow the currency, dates follow the language

Amount formatting is derived from `CURRENCY_METADATA`, never from the interface language.
Measured: `CHF 1234.5` renders `CHF 1'234.50` under `fr_CH`, `de_CH` and `en_CH`, but
`CHF 1234.50` under `it_CH`. Deriving the number format from the language would drop the Swiss
apostrophe the moment a user switches to Italian.

The locale table is protected by owner-only RLS and accepts only the four supported values.
During rolling deployment, the backend may read an older `user_metadata.locale` when no table
row exists, but every new write goes exclusively to the application table. No row means no
server preference: clients preserve their CTA, local snapshot or device/browser resolution.

The landing locale is always explicit in its URL and language selector. It never reads
`navigator.language` to suggest or redirect to another version: a visitor who opened a French
URL stays on the French page until they choose otherwise.

Dates are the opposite: a month spelled out is language, not currency, so date formatting
follows the interface language.

The word _transaction_ itself never appears on screen, in any language. That is a product rule,
not a French one — Pulpe has no bank link, so the noun would promise something the app does not
do. `pnpm test:lexicon` enforces it across all four catalogs, with the banned word declared per
language.

### Three deliberate divergences

A reviewer will read these as mistakes unless they are written down.

1. **French reuses "Prévu" for two concepts** — the `one_off` recurrence type, and the planned
   aggregate that faces the actual one. The other three languages separate them (`One-off` vs
   `Planned`, `Einmalig` vs `Geplant`, `Una tantum` vs `Previsto`), because reusing one word
   there produces an unreadable collision.
2. **"Pointé" is never translated with a banking word.** No _cleared_ or _reconciled_, no
   _gebucht_ or _abgebucht_, no _addebitato_. Pulpe has no bank link: checking a line is a
   manual gesture by the user, and a banking verb would claim a settlement Pulpe never sees.
3. **French reuses "réalisé" for a status and an amount.** The chip on a savings-goal
   withdrawal says "Réalisé" (it happened), and the amount label facing "Prévu" says
   "réalisé CHF 50" (how much happened). The other three languages split the two senses:
   `Completed` vs `actual`, `Erfolgt` vs `tatsächlich`, `Effettuato` vs `effettivo` —
   reusing one word reads fine in French and wrong everywhere else.

## Overflow-prone surfaces

German runs 30 to 40% longer than French. Where space is constrained, the short form is a
separate key rather than a second column in the lexicon above: the shell navigation reads
`navigation.budgetsShort` / `templatesShort` / `savingsGoalsShort`, which every language fills
with its own short form. The balance label needs no such pair — it only ever renders inside
flowing prose, which wraps.

## Plurals

No ICU plugin is added. The 17 existing `…One` / `…Many` key pairs stay selected by the
components' `count === 1` ternary: all four languages sit in CLDR categories `one` / `other`, so
the mechanism holds. iOS uses the String Catalog's _Vary by Plural_ variants, which produce the
same two forms.

Known, pre-existing and out of scope: the ternary renders the plural form for `count === 0`,
which is right in EN/DE/IT and slightly wrong in French.

## System-resolved surfaces on iOS

Two iOS surfaces are rendered by the system, not by the app, so they follow the **device
language** (or the per-app language in iOS Settings) and never the in-app selector:

- The Face ID / Touch ID permission prompt. `InfoPlist.xcstrings` carries its four
  translations, but the system resolves them itself.
- The widget gallery. `configurationDisplayName` and `.description` live in the shared
  catalog, but the gallery process resolves the widget bundle's localization against the
  device language.

The widget **content** is different: the widget target compiles the same
`Localizable.xcstrings` and `Shared/Localization/` as the app (`ios/project.yml`), and both
entry views apply `.environment(\.locale, …)` from the app-group snapshot — so what the
widget displays follows the in-app selector, with one refresh cycle of lag after a language
change. A second catalog for the widget was rejected: it would drift the first time a shared
string is reworded on one side only.

## Localized legal documents

The terms and privacy policy use the same FR / EN / DE / IT catalogs as the rest of the webapp.
French remains canonical; every legal key must exist in all four catalogs, and component tests
lock the number of sections, links, providers, retention periods and locale-formatted date.
Technical identifiers and product names remain unchanged inside the translated documents.

## Localized release notes

The i18n release and every later product release provide FR / EN / DE / IT copy for the landing
changelog, the webapp toast and the iOS feed. French remains canonical and is the only copy used
for GitHub releases. The release validator rejects a missing locale or a divergent projection.

The 37 older releases remain a French archive. Non-French changelog pages link to that archive
instead of mixing French entries into localized content. An older iOS client or a request without
`locale` receives French.

Known and out of scope: `shared/schemas.ts` carries `.default('Mois Standard')`, a French name
the **server** writes into a user's data. It is data, not display, so the catalogs cannot reach
it; fixing it means producing the default in the caller's language, which touches the backend.
