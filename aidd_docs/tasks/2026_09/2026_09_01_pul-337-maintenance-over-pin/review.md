| 🟡 | functional | 1 | `ios/Pulpe/App/AppState+SessionReset.swift:34-36` | CA1 is met only for users without a working Face ID. On `.biometricUnlockSuccess` no probe runs, the user reaches `.authenticated`, and the store loads at `AppRuntimeCoordinator.swift:128-132` then hit the 503. That posts `.maintenanceModeDetected`, but `maintenanceTransition` returns `nil` for `.authenticated` (`AppFlowReducer.swift:55`), the event falls into `eventQueue` and `handleForegroundLifecycleEvent` (`AppState+FlowState.swift:247-251`) drops it. Result: no PIN error (the ticket's harm is avoided) but no maintenance screen either — silent empty/stale data. The plan's own note ("aucun écran PIN n'y est affiché") answers the PIN half of CA1, not the maintenance-screen half | Product call for Maxime: either narrow CA1 to "never a false PIN error" (then this is correct as shipped), or probe on `.biometricUnlockSuccess` too / let the store-load 503 promote `.authenticated` |
| 🟡 | code | 1 | `ios/Pulpe/App/AppState+Maintenance.swift:28-30`, called at `AppState+SessionReset.swift:43` | The probe inherits `AppConfiguration.requestTimeout` = 10 s (`MaintenanceService.swift:22`, `AppConfiguration.swift:98`) and runs *after* `sessionLifecycleCoordinator.handleEnterForeground`, itself bounded at `foregroundUnlockTimeout` = 10 s (`AppConfiguration.swift:129`). Sequential on one `await` chain: a hung Face ID prompt that times out into `.lockRequired` then pays a second 10 s, so up to ~20 s of privacy shield before the PIN pad. PUL-279 capped the unlock at 10 s precisely to avoid a frozen shield (`SessionLifecycleCoordinator.swift:79-81`); this doubles that ceiling and charges a network round trip on every locked resume to cover a rare window | Give the probe its own short budget (2-3 s) instead of `requestTimeout`, or race it against a timeout the way `attemptBiometricUnlockWithinTimeout` (`SessionLifecycleCoordinator.swift:140-151`) already does |
| 🟡 | code | 1 | `ios/Pulpe/App/AppState+Maintenance.swift:29` | `try?` swallows `CancellationError` / `URLError(.cancelled)` alongside real network failures, and the caller writes `authState = .needsPinEntry` unconditionally afterwards. `AppRuntimeCoordinator.swift:118` cancels `foregroundTask` on every re-activation: a background/foreground bounce inside the (now up to 10 s longer) probe window cancels run A, run B computes `.noLockNeeded` and breaks, then run A resumes and still sets `.needsPinEntry` — a spurious PIN prompt for an unlocked user, and no maintenance routing even though the server is in maintenance. The doc comment claims "any failure answers `false`" without acknowledging that cancellation is not a failure to route on | One line after the probe, before the writes: `guard !Task.isCancelled else { return }` |
| 🟢 | rot | 1 | `ios/Pulpe/Features/Maintenance/MaintenanceView.swift:58` | `MaintenanceService.shared.checkStatus()` → `appState.maintenanceChecking()` traces to no acceptance criterion. Behaviourally identical in production (the default dependency at `AppStateDependencies.swift:82-84` is exactly `MaintenanceService.shared.checkStatus()`), and no test covers it. Plan task 4 asked for `retryStartup()` here, which was correctly abandoned; this is a different, unrequested substitution. `CLAUDE.md` "Scope Discipline" puts this in a follow-up block, not the commit | Defensible on its merits (kills a hard-coded singleton in a view) — either drop it from this commit or state it explicitly in the PR body |
